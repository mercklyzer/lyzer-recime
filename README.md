# Recipe Management API

A REST API for managing cooking recipes: create, read, update and delete a
recipe, plus a paged search with optional filters on servings, ingredients
and instruction content. This is my coding exam entry for Recime.

---

## Prerequisites

| Need       | Version    | Notes                                                                                   |
| ---------- | ---------- | --------------------------------------------------------------------------------------- |
| **JDK**    | 17         | `java -version` should report `17.x`.                                                    |
| **Docker** | any recent | With the Compose **v2** plugin (`docker compose`, not `docker-compose`).                  |
| **Maven**  | —          | Not required. The repository ships the wrapper; always invoke it as `./mvnw`.             |

A local PostgreSQL installation is neither needed nor wanted. The development
database and the test database are both pinned to **14.17**, so development,
tests and deployment all see the same engine — testing against a different
version than you deploy defeats the purpose of using a real database at all.

## Running it from a fresh clone

```bash
git clone https://github.com/mercklyzer/lyzer-recime.git
cd lyzer-recime

# 1. Start PostgreSQL 14.17 in the background
docker compose up -d

# 2. Wait for the health check to report "healthy"
docker compose ps

# 3. Run the application — Flyway creates the schema on first start
./mvnw spring-boot:run
```

The API is then served on **http://localhost:8080**. Smoke test it:

```bash
curl -s localhost:8080/api/recipes
# {"content":[],"page":0,"size":20,"totalElements":0,"totalPages":0}
```

Interactive documentation is generated by springdoc and needs no extra setup:

- Swagger UI — **http://localhost:8080/swagger-ui.html**
- OpenAPI document — **http://localhost:8080/v3/api-docs**

### The database container

Defined in [`compose.yaml`](compose.yaml). Data persists in the named volume
`postgres-data` across `up`/`down` cycles.

```bash
docker compose up -d                          # start
docker compose logs -f postgres               # follow logs
docker compose exec postgres psql -U recime -d recime   # psql shell
docker compose down                           # stop, keep data
docker compose down -v                        # stop and drop the volume (fresh database)
```

Defaults:

| Setting  | Value       |
| -------- | ----------- |
| Host     | `localhost` |
| Port     | `5432`      |
| Database | `recime`    |
| User     | `recime`    |
| Password | `recime`    |

If port 5432 is already taken by a local PostgreSQL install, publish another one
and point the application at it:

```bash
POSTGRES_PORT=55432 docker compose up -d
DB_PORT=55432 ./mvnw spring-boot:run
```

### Configuration

No credential is baked into the artifact — every datasource value is read from
the environment with a development-only fallback. The container and the
application are configured independently, which is what lets the two be pointed
at different hosts in a real deployment.

| Side        | Variables                                                         | Default          |
| ----------- | ----------------------------------------------------------------- | ---------------- |
| Container   | `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT` | `recime` / `5432` |
| Application | `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`          | `recime` / `localhost:5432` |

A `.env` file next to `compose.yaml` is picked up for the container side.

### Running the tests

```bash
./mvnw test           # 59 tests
./mvnw clean verify   # full build
```

The suite starts **its own** PostgreSQL 14.17 container through Testcontainers,
so `docker compose up` is not a prerequisite — only a running Docker daemon.
Flyway migrations run in tests as well, which is the only way a migration bug is
caught before deploy.

## API reference

All endpoints live under `/api/recipes`. Search filters are query parameters on
the collection resource — there is no `/search` path and no verb in any URL.

| Operation | Request                    | Success                          |
| --------- | -------------------------- | -------------------------------- |
| Create    | `POST /api/recipes`        | `201 Created` + `Location` header |
| Read      | `GET /api/recipes/{id}`    | `200 OK`                          |
| Search    | `GET /api/recipes`         | `200 OK`, paged                   |
| Update    | `PUT /api/recipes/{id}`    | `200 OK`                          |
| Delete    | `DELETE /api/recipes/{id}` | `204 No Content`, empty body      |

### Create a recipe

```bash
curl -i -X POST localhost:8080/api/recipes \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Kohlrabi Soup",
    "description": "A light autumn soup.",
    "servings": 4,
    "vegetarian": true,
    "instructions": "Sweat the onion, add stock, simmer for 20 minutes, then blend.",
    "ingredients": [
      { "name": "Kohlrabi", "quantity": 2,   "unit": "piece" },
      { "name": "onion",    "quantity": 1,   "unit": "piece" },
      { "name": "salt"                                        }
    ]
  }'
```

```http
HTTP/1.1 201 Created
Location: http://localhost:8080/api/recipes/1
Content-Type: application/json
```

```json
{
  "id": 1,
  "title": "Kohlrabi Soup",
  "description": "A light autumn soup.",
  "servings": 4,
  "vegetarian": true,
  "instructions": "Sweat the onion, add stock, simmer for 20 minutes, then blend.",
  "ingredients": [
    { "name": "kohlrabi", "quantity": 2,    "unit": "piece" },
    { "name": "onion",    "quantity": 1,    "unit": "piece" },
    { "name": "salt",     "quantity": null, "unit": null    }
  ],
  "createdAt": "2026-09-14T09:15:22.767669Z",
  "updatedAt": "2026-09-14T09:15:22.767669Z"
}
```

Three things to note in that response.

`"Kohlrabi"` came back as `"kohlrabi"` — names are canonicalized on write (see
[Assumptions](#assumptions)).

`salt` kept `null` for both quantity and unit rather than being padded with a
zero or a formatted string: "salt, to taste" genuinely has no number, and
`"2 eggs"` genuinely has no unit.

And `quantity` is `2` here, where a subsequent `GET` returns `2.000`. The `201`
body is built from the entity that was just saved, which still carries the scale
Jackson parsed from the request; a later read carries the scale of the
`numeric(10,3)` column. Both are the same number, and any JSON parser reads them
as equal — it is called out because the difference is visible and looks like a
bug until you know why.

Field rules:

| Field                   | Required | Constraint                                     |
| ----------------------- | -------- | ---------------------------------------------- |
| `title`                 | yes      | non-blank, ≤ 200 characters                    |
| `description`           | no       | ≤ 2000 characters                              |
| `servings`              | yes      | positive integer                               |
| `vegetarian`            | yes      | boolean                                        |
| `instructions`          | yes      | non-blank                                      |
| `ingredients`           | yes      | at least one; names unique within the recipe   |
| `ingredients[].name`    | yes      | non-blank, ≤ 120 characters                    |
| `ingredients[].quantity`| no       | positive, ≤ 7 integer and 3 fractional digits  |
| `ingredients[].unit`    | no       | ≤ 50 characters                                |

### Read a recipe

```bash
curl -s localhost:8080/api/recipes/1
```

Returns the full representation shown above. An unknown id is a `404` — see
[Errors](#errors).

### Search recipes

```bash
curl -s -G localhost:8080/api/recipes \
  --data-urlencode 'vegetarian=true' \
  --data-urlencode 'minServings=2' \
  --data-urlencode 'maxServings=6' \
  --data-urlencode 'includeIngredients=kohlrabi,onion' \
  --data-urlencode 'excludeIngredients=pork' \
  --data-urlencode 'instructions=simmer' \
  --data-urlencode 'sort=title,asc' \
  --data-urlencode 'size=20'
```

```json
{
  "content": [
    {
      "id": 1,
      "title": "Kohlrabi Soup",
      "description": "A light autumn soup.",
      "servings": 4,
      "vegetarian": true,
      "ingredients": [
        { "name": "kohlrabi", "quantity": 2.000, "unit": "piece" },
        { "name": "onion",    "quantity": 1.000, "unit": "piece" },
        { "name": "salt",     "quantity": null,  "unit": null    }
      ]
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

Search returns a *summary* representation: `instructions` is deliberately absent,
because a page of twenty full instruction blobs is payload nobody asked for. Ask
for a single recipe to get it.

| Parameter            | Type                    | Meaning                                                                                                   |
| -------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------- |
| `vegetarian`         | boolean                 | Exact match on the stored flag.                                                                            |
| `servings`           | positive integer        | Exact match. Cannot be combined with `minServings`/`maxServings` — that combination is a `400`.             |
| `minServings`        | positive integer        | Servings ≥ this value.                                                                                     |
| `maxServings`        | positive integer        | Servings ≤ this value. `minServings` greater than `maxServings` is a `400`.                                 |
| `includeIngredients` | list, max 20 names      | **AND** — the recipe must contain *every* name listed.                                                      |
| `excludeIngredients` | list, max 20 names      | The recipe must contain *none* of the names listed.                                                         |
| `instructions`       | string                  | Case-insensitive substring of the instruction text. `%` and `_` are matched literally, not as wildcards.     |
| `page`               | integer, default `0`    | Zero-based page index.                                                                                      |
| `size`               | integer, default `20`   | Capped at `100`.                                                                                            |
| `sort`               | `property,asc\|desc`    | Default `title,asc`. Allowed: `title`, `servings`, `createdAt`, `id`. Anything else is a `400`.              |

Both list parameters accept either form, and the two can be mixed:

```
?includeIngredients=onion,garlic
?includeIngredients=onion&includeIngredients=garlic
```

Ingredient matching is **exact and case-insensitive**, not substring:
`excludeIngredients=onion` will not drop a recipe that calls for *spring onion*.
Every filter is optional, and omitting all of them returns every recipe, paged.

### Update a recipe

`PUT` is a **full replacement**, ingredients included — the body carries the
whole recipe, and any ingredient absent from it is deleted. There is no `PATCH`.

```bash
curl -s -X PUT localhost:8080/api/recipes/1 \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Kohlrabi Stew",
    "description": "Heartier, and no longer vegetarian.",
    "servings": 6,
    "vegetarian": false,
    "instructions": "Brown the beef, add the kohlrabi, then simmer for an hour.",
    "ingredients": [
      { "name": "kohlrabi", "quantity": 3,   "unit": "piece" },
      { "name": "beef",     "quantity": 500, "unit": "g"     }
    ]
  }'
```

Returns `200` with the replaced recipe. Validation is identical to create.

### Delete a recipe

```bash
curl -i -X DELETE localhost:8080/api/recipes/1
# HTTP/1.1 204 No Content
```

Ingredient rows go with it, by `ON DELETE CASCADE` in the schema and
`orphanRemoval` in the mapping.

## Errors

Every error response is an RFC 9457 `ProblemDetail`, served as
`application/problem+json`. Controllers and services never build an error
response — they throw, and a single `@RestControllerAdvice` translates.

| Status | Trigger                                                                        |
| ------ | ------------------------------------------------------------------------------ |
| `400`  | Bean Validation failure, malformed JSON, unparseable path variable or query parameter, disallowed `sort` property |
| `404`  | No recipe with that id                                                          |
| `409`  | A database integrity constraint was violated                                    |
| `500`  | Anything unhandled                                                              |

**404**

```json
{
  "type": "https://api.lyzer.dev/problems/recipe-not-found",
  "title": "Recipe not found",
  "status": 404,
  "detail": "Recipe 99 not found",
  "instance": "/api/recipes/99",
  "timestamp": "2026-09-14T09:20:11.816788Z"
}
```

**400 — validation**, with one entry per offending field. Nested paths are
reported positionally, so a client can point at the exact element:

```json
{
  "type": "about:blank",
  "title": "Invalid request",
  "status": 400,
  "detail": "Request validation failed",
  "instance": "/api/recipes",
  "errors": {
    "vegetarian": "must not be null",
    "servings": "must be greater than 0",
    "instructions": "must not be blank",
    "title": "must not be blank",
    "ingredients[0].name": "must not be blank"
  },
  "timestamp": "2026-09-14T09:21:03.863322Z"
}
```

A `500` body never echoes the exception message — the client gets
`"An unexpected error occurred."` and the stack trace goes to the log, once, at
the boundary. Nothing else in the codebase logs and rethrows. `4xx` responses
are client mistakes rather than incidents and are not logged at `error`; request
bodies are never logged at all.

## Data model

Two tables, created by [`V1__create_recipes.sql`](src/main/resources/db/migration/V1__create_recipes.sql).

```
recipes                          recipe_ingredients
-------                          ------------------
id            bigserial PK       id            bigserial PK
title         varchar(200)       recipe_id     bigint FK → recipes(id) ON DELETE CASCADE
description   varchar(2000)      name          varchar(120)
servings      integer  > 0       quantity      numeric(10,3)  NULL, > 0
vegetarian    boolean            unit          varchar(50)    NULL
instructions  text               display_order integer
created_at    timestamptz
updated_at    timestamptz        UNIQUE (recipe_id, name)
                                 INDEX  (name)
```

`UNIQUE (recipe_id, name)` is the storage-level guarantee behind "an ingredient
appears once per recipe", and doubles as the composite index the include filter
probes. The separate index on `name` keeps the ingredient filters off a
sequential scan. `display_order` preserves the order the client sent, so a
recipe's ingredient list reads back the way it was written rather than in
whatever order the database returns rows.

`quantity` is `numeric`, never a floating-point type: `0.1 + 0.2 != 0.3` in
binary floating point, and these are decimal quantities a human typed.

## Design decisions

### Structure

**Package by feature, not by layer.** Everything about recipes lives in
`com.lyzer.lyzerrecime.recipe`, with cross-cutting concerns in `common`. The
payoff is a boundary the compiler can enforce: `RecipeRepository` is
**package-private**, so nothing outside the feature package can reach past the
service into persistence. A layer-first layout (`controllers/`, `services/`,
`repositories/`) forces every type public and turns that boundary into a
convention nobody can check.

**The controller is thin: bind, delegate, map.** No business logic, no
repository access, no `@Transactional`. Method names follow the [official Spring
REST tutorial](https://spring.io/guides/tutorials/rest) — `one`, `all`, `newRecipe`, `replaceRecipe`, `deleteRecipe` —
while service methods are named for what they do to the domain (`create`,
`findById`, `search`).

**Entities never cross the boundary.** Requests and responses are records in a
`dto/` subpackage, named by role (`CreateRecipeRequest`, `RecipeResponse`,
`RecipeSummaryResponse`), never `XDto`.

### Domain model

**Ingredients are owned line items, not a shared catalog.** A row is "200 g of
onion, for recipe 7" — it has no meaning apart from its parent, so it is a
one-to-many child with `orphanRemoval`. A shared `ingredients` table with a join
table sounds more scalable, but it buys dedup-on-write, orphan cleanup and a
much fussier `PUT` reconciliation for requirements this brief never states.
*Revisit when ingredients gain attributes of their own — allergens, nutrition,
supplier — because that is the point at which the data genuinely belongs to the
ingredient rather than to the recipe.*

**Ingredient names are normalized on write**, via a single function
(`IngredientNames.normalize` — `trim().toLowerCase(Locale.ROOT)`). Write mapping,
the uniqueness validator and the search filters all call it, which is what makes
`?includeIngredients=Onion` match a stored `"onion"`.

**Instructions are one `TEXT` column.** The brief asks for instruction content
search, and one column makes that a clean case-insensitive `LIKE`. A
`recipe_steps` child table is more faithful to how recipes are actually written,
but it turns content search into a second joined collection needing `DISTINCT`
care, for no additional requirement coverage. *Revisit when steps need
individual identity — per-step timers, images, or check-off state.*

**`vegetarian` is a column the client sets, not something derived.** Inferring
it from ingredient names is guesswork the moment you hit "stock", "gelatin",
"parmesan" or "Worcestershire sauce", and a filter that is quietly wrong is worse
than one that is honestly manual. *Revisit when ingredients become catalog
entries that can carry their own dietary flags — then derivation is a lookup
rather than a guess.*

**`PUT` replaces; there is no `PATCH`.** One write path is one set of invariants
to maintain and one shape to validate. It also sidesteps the question `PATCH`
always raises — whether a `null` field means "clear it" or "leave it alone" —
which JSON alone cannot answer.

The interesting part is *how* the replacement is applied. Ingredient rows are
matched to the request **by normalized name** and reused, rather than deleted and
reinserted wholesale. With `IDENTITY` ids Hibernate cannot defer a child insert —
it needs the generated key — so the insert of a name that survives the update
would reach PostgreSQL before the orphan delete of its old row, and
`UNIQUE (recipe_id, name)` would reject it. Matching by name makes the deleted
and inserted sets disjoint, so flush ordering stops mattering at all.

### Search

**`Specification`s, not derived query methods.** Seven optional filters combined
freely is `2^7` possible queries; one derived method per combination does not
scale past about three filters. Each filter here is one composable predicate that
returns `null` when its parameter is absent, and `Specification.allOf(...)`
drops the nulls. Adding a filter is one method and one criteria field, with no
change to anything that already exists.

*A note for later:* `allOf`'s null-tolerance is safe **only under AND**. If an OR
mode is ever added, an absent predicate would silently *widen* the result set
instead of narrowing it.

**`includeIngredients` is AND, and it is a subquery rather than a join.** This is
the one genuinely hard query in the API — relational division: match a parent row
only when a whole set of child rows exists. Two formulations look correct and are
not.

```sql
-- WRONG: this is OR, not AND
select r.* from recipes r
join recipe_ingredients ri on ri.recipe_id = r.id
where ri.name in ('onion', 'garlic');
```

A joined row carries exactly one name, so it cannot equal both. Writing the names
as two equality predicates on the *same* join gives `name = 'onion' and name =
'garlic'`, which matches nothing at all.

```sql
-- WRONG: this matches almost everything
where ri.name != 'pork';
```

Any recipe with two or more ingredients has *some* row that is not pork, so pork
recipes come back too. The question has to be asked of the recipe, not of a row.

So inclusion collects the recipe ids whose ingredient names are in the list and
keeps only those that matched every one, and exclusion is a single correlated
`NOT EXISTS` over an `IN` list:

```sql
where r.id in (select ri.recipe_id from recipe_ingredients ri
                where ri.name in ('onion', 'garlic')
                group by ri.recipe_id
                having count(*) = 2)
  and not exists (select 1 from recipe_ingredients ri where ri.recipe_id = r.id and ri.name in ('pork'));
```

The `having` count is exact because names are de-duplicated before the query is
built and `UNIQUE (recipe_id, name)` rules out a repeated row — so "matched every
requested name" and "matched N rows" are the same question.

Joins would break paging independently of correctness: they multiply rows, so the
count query behind `totalElements` would count joined rows rather than recipes.
`paginatesResultsAndReportsCorrectTotal` exists to catch exactly that.

Both ingredient lists are capped at twenty names by `@Size(max = 20)` — more
than a search realistically carries, and a list parameter with no ceiling is one
fewer thing an unfriendly client can lean on. *Revisit when users start
complaining about the limit.*

**Instruction search escapes `LIKE` metacharacters.** Without it, a search for
`50%` becomes `LIKE '%50%%'` and the user's literal `%` silently becomes a
wildcard.

**Search is always paged.** `Page<RecipeSummaryResponse>`, never an unbounded
`List` — an endpoint that can return the whole table is a production incident
waiting for the table to grow. `size` is capped at 100 so `?size=100000` cannot
be used as a lever.

`sort` is checked against an allowlist rather than passed through, because
`Pageable` binds arbitrary property names straight into the query — an
unvalidated one is both a `500` on a typo and an information leak on a
well-chosen guess. `id` is always appended as a tiebreaker, without which two
recipes sharing a title can swap places between page 1 and page 2 and a row is
silently skipped. *Revisit when deep pages matter: `OFFSET` makes the database
walk and discard every skipped row, and keyset (cursor) paging is the fix.*

### Errors

**One `@RestControllerAdvice` extending `ResponseEntityExceptionHandler`**,
scoped with `basePackages` to this application. Extending the base class inherits
`ProblemDetail` responses for the ~15 Spring MVC exceptions rather than
reimplementing them; the package scope matters because the catch-all `Exception`
handler would otherwise swallow springdoc's own spec-generation failures into a
generic `500`.

**Duplicate ingredient names are rejected at the boundary, not by the database.**
`["onion", "Onion"]` is a malformed request, so a custom `@UniqueIngredientNames`
constraint turns it into a `400` naming the offending field, instead of letting
it surface as an opaque `uq_recipe_ingredient_name` violation. The database
constraint stays as the backstop for writes that never pass through the DTO.

**`409` is deliberately vague.** It catches every integrity violation, so naming
one would misreport the others. Constraint and column names stay in the log —
they are schema details, not client-facing information.

## Assumptions

Where the brief was silent, these are the readings this implementation committed
to.

1. **Ingredient names are canonicalized on write** — trimmed and lower-cased.
   `"  Onion "` is stored and returned as `"onion"`. Presentation casing is a
   client concern; the API's job is to make matching reliable.
2. **`vegetarian` is asserted by the client, not derived** from the ingredient
   list.
3. **An ingredient name is unique within a recipe**, enforced by a database
   constraint. Quantity and unit are free-form strings and numbers — no unit
   vocabulary, no conversion, no validation that "g" is a real unit.
4. **`PUT` is a full replacement**, including the ingredient list. Omitting an
   ingredient deletes it. There is no `PATCH`.
5. **Search is always paged.** No endpoint returns an unbounded result set.
6. **There is no authentication or authorization.** Every recipe is
   world-readable and world-writable, and there is no notion of an owner. This is
   the assumption with the widest blast radius, and the first thing that would
   need to change for any deployment that is not a demo — a `POST` that creates a
   recipe for *someone* requires a principal, which changes the schema, not just
   the filter chain.

## Testing strategy

59 tests, weighted toward the layer most likely to be wrong.

- **Repository and `Specification`** (`@DataJpaTest`) — the largest group: every
  search filter, pagination and count correctness, and `PUT` reconciliation.
- **Controller slice** (`@WebMvcTest`, service mocked) — status codes, the
  `Location` header, validation `400`s, `ProblemDetail` shapes, query-parameter
  binding.
- **End-to-end** (`@SpringBootTest`, one test) — create → fetch → search →
  update → delete against the real stack.
- **Validator unit test** — the `@UniqueIngredientNames` constraint in isolation.

Database-backed tests run against Testcontainers PostgreSQL **14.17**, the same
version `compose.yaml` runs — never H2. There are no standalone service unit
tests; the service is delegation, and its cases are covered through the slices
above.
